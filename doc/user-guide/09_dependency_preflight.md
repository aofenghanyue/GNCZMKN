# 09 依赖预检查的新默认路径

这一页补充说明当前框架在“依赖注入”和“构建期诊断”上的最新默认做法。

## 9.1 这一轮解决的核心问题

在前几轮整理之后，框架里还剩一个实际摩擦点：

- `injectDependencies()` 才是真正的依赖事实源
- 但部分装配型组件还要额外维护一份 `getDependencies()`
- 这样会出现“声明一遍，绑定一遍”的双写
- 一旦两处名字漂移，就会产生新的维护负担

更稳妥的方向不是继续为 declarer 发明更多样板，而是让框架直接从真实的 `injectDependencies()` 得到构建期诊断。

## 9.2 现在的默认行为

现在对于用 `bind(...)` 写出的必需依赖，构建器会在 build 阶段直接预检查真实绑定逻辑。

这条链路的含义是：

- `bind(member, "name")` 表示必需依赖
- `bindIfPresent(member, "name")` 表示合法可选依赖
- 构建器会执行真实的 `injectDependencies()`
- 如果同一个组件缺多个必需依赖，会一次性聚合报出整组问题
- 这些诊断来自真实绑定路径，而不是另一份手写声明副本

因此，默认情况下你只需要把 `injectDependencies()` 写对，框架就已经能在构建期把大多数依赖错误拦下来。

## 9.3 `IDependencyDeclarer` 现在还用来做什么

`IDependencyDeclarer` 没有被删除，但它的定位已经收紧成增强层，而不是默认必需层。

适合继续使用 declarer 的情况：

- 你想给缺依赖问题写更强的领域语义描述
- 你希望把“依赖为什么存在”显式写进代码，而不是只依赖绑定名
- 你的组件是一个复杂装配点，团队希望保留额外的人工依赖说明

不适合把 declarer 当成默认动作的情况：

- 只是重复 1 到 2 个同作用域的 `bind(...)`
- 只是为了让构建期能报错
- 只是因为模板里看起来“好像应该实现一下”

换句话说，declarer 现在是“可选增强”，不是“先写了再说”。

## 9.4 仓库里的当前实践

仓库内的 starter/example 组件现在已经按这条主线收口：

- `Dynamics3DOF_SphericalEarth` 不再额外维护 declarer
- `CavhAerodynamics` 不再额外维护 declarer
- 这两个组件依然会在构建期被检查
- 并且如果缺多个必需依赖，会一次性报出整组问题

这说明当前仓库已经不再依赖 declarer 才能支撑装配型组件的构建期诊断。

## 9.5 对用户写组件的直接建议

推荐顺序：

1. 先把角色接口选对。
2. 在 `injectDependencies()` 里用 `bind(...)` / `bindIfPresent(...)` 把真实依赖写清楚。
3. 先让最小链路跑通。
4. 只有在你确实需要更强语义描述时，再补 `IDependencyDeclarer`。

推荐把关注点分开：

- 真实绑定关系：写在 `injectDependencies()`
- 构建期自动拦截：交给预检查机制
- 额外语义说明：按需再加 declarer

## 9.6 这一变化对你意味着什么

对于框架使用者，这一轮最直接的收益不是“多了一个新接口”，而是少了一份必须维护的重复信息。

现在更接近一种稳定约定：

- 依赖是什么，看真实绑定代码
- 缺依赖时，构建期就能拦住
- 复杂场景要更漂亮的报错，再额外写 declarer

这也更符合本框架当前的主线：先把边界、语义和默认路径收紧，而不是继续增加新的抽象层。
