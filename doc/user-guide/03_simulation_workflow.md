# 03 如何组织一套仿真模型

## 3.1 先不要从“代码文件”出发，要从“模型职责”出发

对于这个框架，正确的建模顺序不是先想“我要新建几个 `.hpp`”，而是先回答下面几个问题：

1. 我要仿真的对象是什么
2. 它的状态由谁推进
3. 它所在环境由谁提供
4. 制导/控制/导航分别承担什么职责
5. 哪些量需要输出
6. 何时停止仿真

把这六件事理顺以后，再落到接口和组件，会比先写代码清晰得多。

## 3.2 推荐的建模拆分法

### 第一步：确定场景拓扑

当前框架支持三种拓扑：

- 单飞行器场景
- 环境 + 单飞行器
- 环境 + 多飞行器

如果你的任务只是一个飞行器在固定环境中运动，优先使用单飞行器配置。只有在下面情况出现时，才建议进入多实体模式：

- 需要显式建模多个飞行器
- 需要跨实体访问目标状态
- 需要把某些环境组件放到 `environment` 作用域统一管理

### 第二步：先定义动力学，再补外围算法

动力学组件是仿真骨架的中心，因为它决定：

- 状态维数
- 状态变量名字
- 微分方程
- 积分器适用性
- 哪些状态能被导航、传感器、真值状态读取

建议先把动力学状态和输入关系设计好，再往外加：

- 环境模型
- 传感器
- 导航
- 制导
- 控制

### 第三步：把“输入源”设计清楚

当前仓库里有两条典型链路：

#### 简化 6DOF/点质点链路

- `ConstantGuidance` 输出加速度指令
- `SimpleDynamics` 直接把加速度作为状态导数输入
- `SimpleNavigation` 直接从动力学读位置速度

这条链路的特点是简单、快速、适合做框架验证和最小实验。

#### 3DOF 再入链路

- `CavhProgrammedAoA` 提供攻角/倾侧角指令
- `CavhAerodynamics` 提供气动系数
- `CavhMass` 提供质量属性
- `StandardAtmosphere` 和 `SphericalGravity` 提供环境
- `Dynamics3DOF_SphericalEarth` 综合这些输入推进状态

这条链路更接近“领域模型装配”的真实方式。

## 3.3 组件协作的标准思路

从当前代码可以总结出一套非常清晰的职责划分：

| 类别        | 主要职责            | 典型接口                                             |
| --------- | --------------- | ------------------------------------------------ |
| 环境组件      | 提供外部物理环境        | `IAtmosphereModel`、`IGravityModel`、`IEarthModel` |
| 动力学组件     | 定义状态并推进状态       | `IDynamicsModel`                                 |
| 传感器组件     | 把真值或状态转换为测量量    | `IImuSensor`、`IGpsSensor`                        |
| 导航组件      | 生成导航解           | `INavigation`                                    |
| 制导组件      | 生成制导指令          | `IGuidance6DOF`、`IGuidance3DOF`                  |
| 控制组件      | 把制导指令变成控制/执行器命令 | `IController`                                    |
| 质量/气动组件   | 为动力学提供模型参数      | `IMassProperty`、`IAeroCoefficients`              |
| 真值/状态提供组件 | 提供可复用状态读取接口     | `IPositionProvider`、`IVelocityProvider`          |

如果一个组件承担了太多职责，通常说明建模拆分还不够清楚。

## 3.4 执行顺序如何影响模型

框架按注册顺序遍历组件。对每个仿真步：

- 动力学组件会被积分器推进
- 普通组件会在各自频率允许时调用 `update(dt)`
- 之后统一记录数据

这意味着：

- 如果某组件依赖另一个组件在本步先更新，注册顺序就要有意识
- 若某组件频率比主仿真频率低，它只会在间隔步执行
- 导航、传感器、制导等离散模块要明确自己需要多少采样频率

在当前实现里，组件频率不是连续时间调度，而是“主步长上的整步间隔”。所以最佳实践是让主步长足够小，再用频率机制降低非关键模块更新开销。

## 3.5 推荐的任务搭建流程

对于一个新任务，建议按下面顺序迭代：

1. 先让动力学单独跑起来
2. 给动力学补一个最简单的输入源
3. 给关键状态增加 `IObservable`
4. 确认 CSV 输出正确
5. 再增加环境、质量、气动、传感器
6. 最后再加导航、制导、控制的闭环逻辑

这样做有两个好处：

- 每一步都能独立验证
- 出问题时很容易定位是装配问题、状态问题还是算法问题

## 3.6 命名规则就是接口连接规则

框架里 `name` 不是装饰信息，而是依赖注入时真正使用的实例名。比如：

- `guidance`
- `dynamics`
- `nav`
- `imu`
- `aero`
- `mass`

很多内建组件在 `injectDependencies()` 里就是按这些常见名字获取依赖。因此，推荐优先沿用仓库现有命名习惯，除非你明确知道自己要改成什么。

多实体模式下命名会自动扩展成：

- `vehicle_id.component_name`
- `env.component_name`

同作用域组件可以用短名依赖，跨实体访问时用全名。

## 3.7 什么量应该暴露成可观测字段

一个好的仿真模型，不是把所有内部变量都输出，而是有选择地暴露：

- 任务判据相关量
- 算法闭环关键量
- 可用于验模的物理量
- 可用于停止条件的量

仓库中现有组件已经给出较好的风格参考：

- 动力学输出位置、速度、马赫数、高度、攻角等
- 制导输出指令量和时间戳
- 气动输出 `CL`、`CD`、升阻比
- 质量组件输出质量

一般不建议把纯内部临时变量都暴露出来，否则配置和 CSV 很快会失去可读性。

## 3.8 一套好的模型目录长什么样

对这个框架来说，最实用的组织方式通常是：

- `user/components/guidance/`
- `user/components/navigation/`
- `user/components/controller/`
- 必要时增加 `user/components/dynamics/`、`environment/`、`vehicle/`
- `user/config/missions/` 保存不同任务文件

配套原则：

- 一个组件一个头文件
- 文件名和类名保持对应关系
- mission 文件按任务目的命名，而不是按日期乱命名

## 3.9 面向任务的思维方式

最适合本框架的工作方式不是“我有一堆类，看看怎么拼”，而是：

- 这是一个什么任务
- 任务需要哪些角色
- 每个角色用哪个接口表示
- 哪些角色现在可以用内建组件
- 哪些角色必须自己实现

一旦按任务角色来拆，这套框架的设计就会非常顺手。
