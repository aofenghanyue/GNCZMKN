# 设计决策

这篇文档记录当前仍有效的架构决策。它不是教程，也不按历史阶段组织。

## 1. 使用四层架构

框架分为 Core、Subsystem Plugin、System Plugin、Project Component 四层。

这样做的原因是：内核只提供装配和调度机制，物理模型放在子系统插件，跨模型的系统能力放在系统插件，任务算法放在用户项目。边界清楚后，项目算法不会反向污染基础插件，基础插件也不需要知道具体任务。

## 2. 插件使用编译期注册

当前插件不是运行时动态库。内置插件由 `_builtin_plugins.hpp` 纳入编译，项目组件由 CMake 生成的 `auto_registered_components.hpp` 纳入编译。

这样做牺牲了运行时热插拔，但换来更简单的调试、更明确的依赖顺序和更低的部署成本。项目仍处于开发初期，编译期注册比动态加载更适合当前阶段。

## 3. 任务配置采用 entity-first

任务顶层必须使用 `entities[]`。环境和飞行器都作为实体装配，组件归属于实体。

这个决策消除了单飞行器和多飞行器之间的结构分叉。单飞行器任务不需要单独适配层，多飞行器任务也只是增加更多 `vehicle` 实体。

## 4. 组件名称必须带实体作用域

环境组件统一注册为 `env.*`，飞行器组件注册为 `<entity_id>.*`。

这样做让日志、停止条件、服务绑定和依赖诊断使用同一套命名规则。组件代码仍可通过 `ScopedRegistry` 使用局部名绑定同实体依赖，但配置文件应优先写完整名。

## 5. 服务有明确作用域

服务可以配置在 `global_services`、环境实体 `services`、飞行器实体 `services` 中。组件接收服务的顺序是 `global -> environment -> vehicle`。

这个决策让共享能力和飞行器私有能力有清楚边界。只有所有实体都要共享的能力才应放进 `global_services`。

## 6. 服务绑定允许延迟执行

有些服务需要引用组件，但服务安装发生在组件装配过程中。为避免声明顺序限制，服务安装器可以把绑定动作放进 `deferred_actions`。

框架会在所有实体组件注册完成后执行延迟动作。`soviet_coord` 服务就是这个模式：先创建服务，再等组件注册完成后绑定 `IEarth` 和速度方向提供者。

## 7. SimulationBuilder 不负责实体细节

`SimulationBuilder` 只做高层构建编排。`MissionAssembler` 负责把 `entities[]` 转换成服务、组件和注册表内容。

这个决策限制了 builder 的膨胀。以后扩展实体装配规则，应优先修改 `MissionAssembler`，而不是继续往 `SimulationBuilder` 塞分支。

## 8. 仿真主循环使用固定步长

当前运行时采用固定步长。`simulation.dt` 同时驱动积分器、组件调度、日志记录和停止条件检查。

固定步长让数据记录和组件执行频率更容易解释。自适应积分可以在以后引入，但需要重新定义日志采样、组件调度和终止条件的语义。

## 9. ADR 不作为主要学习材料

历史 ADR 已被压缩到本文件。新读者应该先读教程和架构说明，再按需查看设计决策。

这样做能避免文档再次被实施阶段牵着走。文档描述的是当前架构，不是迁移过程。
