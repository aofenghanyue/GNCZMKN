# 设计决策

这篇文档记录当前仍然有效的架构取舍。它不是迁移日志，也不按历史 phase 排列。

## 1. 任务配置采用 entity-first

顶层 mission 必须使用 `entities[]`。

原因：

- 单飞行器和多飞行器使用同一套结构
- 所有组件都有明确归属实体
- 服务作用域、日志命名、停机条件命名都能统一

当前正式基线是：

- 只支持 `entities[]`
- 不再兼容旧式根级 `components` / `services` / `vehicles`

## 2. 组件命名始终带实体作用域

当前命名规则固定为：

- 环境组件：`env.<component_name>`
- 飞行器组件：`<entity_id>.<component_name>`

原因：

- 日志、停机条件、服务绑定和诊断都依赖稳定命名
- 单飞行器和多飞行器不再需要两套规则
- 同一实体内可以复用局部组件名，跨实体时仍保持唯一

当前正式基线是：

- 不再保留单飞行器空前缀分支

## 3. 服务必须有明确作用域

服务可以出现在：

- `global_services`
- 环境实体 `services`
- 飞行器实体 `services`

组件接收服务的顺序固定为：

```text
global -> environment -> vehicle
```

这样可以把共享能力、环境能力和飞行器私有能力明确分层。

## 4. 服务绑定允许延迟执行

有些服务需要绑定组件，但服务安装发生在组件装配过程中。为避免声明顺序限制，服务安装器可以把绑定动作放进 `deferred_actions`。

框架会在所有实体组件注册完成后统一执行这些动作。

## 5. `SimulationBuilder` 只做高层编排

当前构建职责拆分为四块：

| 类型 | 职责 |
| --- | --- |
| `SimulationBuilder` | 读配置、设置仿真参数和积分器、串联装配、验证、停机条件和 logger 初始化、汇总诊断 |
| `MissionAssembler` | 安装全局服务、按实体创建服务和组件、注册接口、执行延迟服务动作 |
| `ValidationPipeline` | 执行 `DependencyValidator`、build 期依赖预检、产出验证错误和警告 |
| `StopConditionBuilder` | 解析 `simulation.stop_conditions`，查找字段并注册终止条件 |

这个边界的目的很直接：避免 `SimulationBuilder` 再次膨胀成“什么都做”的巨类。

## 6. 运行循环使用固定步长

当前仿真循环围绕固定步长 `simulation.dt` 组织。它同时驱动：

- 积分器
- 组件调度
- 自动记录器
- 停机条件检查

这样做的好处是：

- 记录数据更稳定
- 组件频率换算更直接
- 用户更容易理解每一步发生了什么

代价是当前不支持可变步长积分器。若以后引入自适应步长，需要同时重构积分、调度、日志采样和停机条件语义，而不是只改积分器接口。

## 7. 编译期注册优先于运行时动态发现

当前插件和项目组件都通过编译期纳入：

- 内置插件由 `_builtin_plugins.hpp` 收进命令行入口
- 项目组件由 CMake 生成的 `auto_registered_components.hpp` 收进编译

这样做放弃了运行时热插拔，但换来：

- 更简单的调试路径
- 更明确的依赖顺序
- 更低的部署复杂度

## 8. 当前文档基线高于历史实施细则

`temp/seeByAgent/*` 继续保留为历史评审材料，但不再作为运行时或用户文档的正式真源。

正式真源是：

- `README.md`
- `doc/`

与历史实施细则相比，当前正式差异只有两条：

- 不再支持旧式根级 mission
- 不再保留单飞行器空前缀命名
